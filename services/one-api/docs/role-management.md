# Role management

User department affiliations are stored in `government_organization_members` with a composite user/node key. A user may have zero or multiple direct affiliations. In the user editor, the Department field below Role selects each path level by level, adds multiple selections, and saves them with the account through `PUT /api/user/` as `organization_node_ids`; the existing administrator confirmation still applies to the user form. The organization page lists direct members and offers root administrators a searchable batch member selector. Saving either view replaces only that user's affiliations or that node's members, preserving memberships at other nodes and permission roles. The membership replacement validates all selected records in one database transaction. Knowledge Library reads the same nodes and memberships to display full department paths, including multiple affiliations, and does not use the legacy `users.department_name` text for personnel cards or filters. Nodes with active members cannot be deleted. Clicking an organization row toggles its children and members; the independently scrollable tree does not stretch the detail card.

Role definitions are stored in the main OneAPI database's `public.roles` table. `users.role` stores the assigned code; these definitions are not in the account-center database.

Creating a role requires a name and `role_type` (`member` or `admin`). The server allocates an unused code within the existing authorization bands: members 2–9, administrators 10–99. It also skips codes referenced by legacy users without a role definition. Clients cannot choose a code or create a super-administrator. Only a super-administrator may create or delete administrator roles. Existing numeric authorization comparisons remain unchanged.

The built-in member (1), super-administrator (100), and any role marked `is_builtin` cannot be deleted. `DELETE /api/role/:role` rejects roles referenced by any user, including soft-deleted users. Reassign users before deleting a custom role. Deletion does not alter user accounts. Successful deletion removes the role from the frontend's role cache.

The create dialog offers member/administrator selection, automatic numbering, inline failures and a pending-request guard. Deletion requires a separate confirmation. The role list retains model configuration and labels each role's authorization category. The model dialog's select-all and invert actions apply to the complete displayed catalog, including scrolled-off entries. They preserve existing permissions absent from the catalog and only persist after Save; Cancel discards changes. Bulk actions are disabled while loading or when the catalog is empty.

User Permissions → Organization Structure stores an independently editable government organization tree in `government_organization_nodes`. Root administrators can create top-level or child nodes with free-form names and types, reorder or move nodes, and delete unused leaves. There is no fixed depth and no starter data. A successful list response always contains an array, including `[]` for an empty tree. The page distinguishes failed reads from empty data and offers a retry before enabling edits. The API rejects missing parents, ancestry cycles, and deletion while a child or role still refers to a node. Administrators can read the tree; only the built-in super-administrator can change it.

Role creation and configuration can select multiple organization nodes. The selected IDs are stored in `roles.permissions.organization_node_ids` and validated against the current tree. This association is administrative metadata; it does not change existing user authorization, model access, enterprise billing organizations, or data visibility. Assigning a user to a role continues to use `users.role`.

Verification: `go test ./controller -run 'TestManagedRoleLifecycle|TestGovernmentOrganizationTreeAndRoleReferences' -count=1` and the frontend `RolePermissions.test.js`. Go tests use isolated SQLite or a temporary PostgreSQL schema when `DSH_SKILL_INSTALLATION_TEST_POSTGRES_DSN` is supplied; never use production credentials for tests.

User department assignments use one dropdown containing a collapsible organization tree. Clicking a branch row expands or collapses it; only leaf departments can be selected. Selecting a leaf closes the dropdown. Reopen it to add a concurrent appointment; selected departments show a check mark and removable tags. Existing parent affiliations remain visible until explicitly removed. Loading failures keep the existing selection and block affiliation submission until a successful retry; login, permission, and non-JSON API responses have distinct diagnostics.
