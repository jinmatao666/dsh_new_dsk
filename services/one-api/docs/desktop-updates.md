# Desktop update distribution

English | [中文](desktop-updates.zh.md)

## Administrator workflow

The Version Release page filters desktop packages by OS and architecture and lists them as independent releases. Only the system root administrator may list, upload, publish or withdraw releases. Enter the stable version, OS and architecture, then upload one Runner-produced signed platform ZIP with plain-text notes. Multipart uploads require `version` and `platform`; both must exactly match the signed manifest and cannot relabel the package. A mismatch rejects the upload and removes staged files. Uploading never publishes. Publication requires a separate confirmation and rechecks signatures against the configured public key. Windows ARM64 has no build target; Windows supports x64, while macOS and Linux support x64 and ARM64. Legacy mobile, website and service-restart records remain at `/operation/version-release/legacy`, separate from desktop updates.

The release ZIP contains exactly `release.json`, `release.json.sig` and one artifact named by the manifest. The manifest and artifact both use Tauri-compatible base64 Minisign prehashed signatures. The manifest binds product `com.wanwei.harness`, stable `x.y.z` version, platform, artifact filename, byte count, SHA-256 and artifact signature. A missing public key disables uploads and publication; the administrator page never accepts a private key.

Each OS/architecture has its own publication pointer. Missing platform releases return no update. Withdrawal hides the current release without reverting to older uploads. A persistent high-water version prevents publishing a lower version after withdrawal. Re-uploading an existing platform/version is rejected; issue a higher version instead. The list retains the latest 200 uploads; older records and artifacts are not deleted automatically.

## Server configuration

| Variable | Meaning |
|---|---|
| `DESKTOP_UPDATE_DIR` | Private artifact directory; default `/data/wanwei/desktop-updates` |
| `DESKTOP_UPDATE_PUBLIC_KEY` | Base64 public-key file produced by Tauri; never a private key |
| `DESKTOP_UPDATE_PUBLIC_URL` | Public server base URL, optionally including a reverse-proxy prefix; falls back to `SERVER_ADDRESS` |
| `DESKTOP_UPDATE_MAX_BYTES` | Maximum artifact bytes; default 2147483648, configurable from 1024 to 8589934592 |

The shared Compose configuration maps `DSH_DESKTOP_UPDATE_HOST_DIR` (default `/data/wanwei/desktop-updates`) to container `/data/desktop-updates`; it also passes `DSH_DESKTOP_UPDATE_PUBLIC_KEY` and `DSH_DESKTOP_UPDATE_MAX_BYTES`. OneAPI startup adds `desktop_updates` and `desktop_update_channels` in the existing database. Back up both database and artifact directory. Use Go 1.21 or newer for the signature dependency. New tests use a pure-Go SQLite driver on Windows; the production SQLite driver is unchanged.

Expose `/desktop-updates/` through the existing OneAPI public entry, not through a directory listing. The check endpoint is `/desktop-updates/{target}/{arch}/{currentVersion}`; it returns Tauri update JSON or HTTP 204. Artifact URLs are generated from the configured base, never untrusted request headers. Draft and withdrawn artifacts return 404. Version and download responses use `Cache-Control: no-store`. Administrative endpoints are under `/api/desktop-updates` with root authentication and operation-audit registration.

The proxy must permit the chosen upload size and sufficient request duration. Uploads are bounded and streamed to private temporary files; one upload is admitted per server process. Successful uploads are published into unique directories before recording the database row. Rejected uploads remove their staging files. An abrupt process/host failure may leave `.upload-*` directories or an unreferenced artifact directory; operators may inspect and clean those only while no upload is running. Multiple instances must share both database and storage. Publication row locks serialize a platform on PostgreSQL/MySQL; SQLite write contention fails the request for an administrator retry rather than publishing a partial state.

## Runner distribution

The manual desktop workflow exposes `build_update_bundles`, default false. Ordinary installer builds do not need signing keys. Signed builds require repository Secrets `TAURI_SIGNING_PRIVATE_KEY`, optional `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, and the public repository variable `DSH_DESKTOP_UPDATE_PUBLIC_KEY`. No key is generated by this workflow. Keep a separate secure backup; changing Git repositories does not require changing the key pair.

The workflow enables Tauri updater artifacts and exports a separate `wanwei-update-*.zip` artifact per platform. Download and extract the GitHub artifact wrapper, then upload the inner release ZIP through the administrator page. Windows uses NSIS EXE, macOS uses `.app.tar.gz` rather than DMG, and Linux uses AppImage. The exporter accepts stable versions and artifacts up to 2 GiB, uses streamed ZIP output, and refuses to overwrite an existing output ZIP. Package construction does not publish to the server.

## Verification and limits

Run `go test ./controller -run '^TestDesktopUpdate' -count=1` from `services/one-api`, and `node --test products/wanwei-desktop/scripts/package-update.test.mjs products/wanwei-desktop/scripts/prepare-runner-config.test.mjs` from the repository root. The latter generates disposable test keys, signs with the actual Tauri CLI, imports the resulting ZIP through the real upload handler and checks publication. Test keys are deleted and never become production configuration.

The public update JSON includes the original manifest text and its signature so the native client can verify version and platform metadata independently of HTTP. Native checking, download confirmation, task exclusion and cooperative shutdown are owned by the desktop shell, not this service. No production keys, server deployment or real Windows/macOS/Linux upgrade is performed by these tests. Signed HTTP downloads do not provide transport confidentiality or authenticate unsigned update availability and release notes. Prefer HTTPS; signature verification is not a replacement for TLS or Windows/macOS system code signing.
