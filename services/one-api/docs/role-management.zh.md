# 角色管理

用户部门归属存储在 `government_organization_members` 中，使用用户与节点的联合主键。用户可以没有部门，也可以直接归属多个部门。编辑用户时，“部门”字段位于“角色权限”下方，按层级逐级选择并可添加多条归属；“保存用户”通过 `PUT /api/user/` 的 `organization_node_ids` 一并提交，沿用用户表单的管理员确认。组织页展示直属成员，超级管理员可搜索并批量管理成员。任一入口保存时仅替换当前用户的归属或当前节点的成员，保留其他节点的兼任归属和权限角色。成员关系替换在同一数据库事务内校验全部选择项。知识库读取同一份节点与成员关系，展示完整部门路径和多个归属；人员卡片及筛选不再读取旧的 `users.department_name` 文本。存在有效成员的节点不能删除。点击组织行可展开、收起下级节点与成员；组织树独立滚动，不撑高详情卡片。

角色定义位于 OneAPI 主数据库的 `public.roles` 表，`users.role` 保存分配的编号；角色定义不在账号中心数据库中。

创建角色需要名称和 `role_type`（`member` 普通成员或 `admin` 管理员）。服务端在现有权限区间内分配空闲编号：普通成员为 2–9，管理员为 10–99。历史账号引用但没有角色定义的编号也会跳过。客户端不能指定编号或创建超级管理员。只有超级管理员能够创建、删除管理员角色。现有按编号比较的鉴权逻辑保持不变。

内置普通成员（1）、超级管理员（100）及所有标记为 `is_builtin` 的角色不可删除。`DELETE /api/role/:role` 会拒绝仍被任何账号引用的角色，包括软删除账号。删除自定义角色前需要先为用户更换角色。删除角色不修改用户账号。删除成功后同步清理前端角色缓存。

新建弹窗支持普通成员／管理员选择、自动编号、行内错误提示及请求期间禁止重复提交。删除需要单独确认。角色列表保留可用模型配置，并标明每个角色所属的权限类别。模型弹窗的“全选／反选”作用于当前目录中的全部模型，包括滚动区域外的条目；保留目录中暂未出现的已有权限，点击“保存”才生效，“取消”则丢弃修改。加载中或目录为空时禁用批量操作。

用户权限 → 组织架构将独立的政务组织树保存在 `government_organization_nodes`。超级管理员可以用自定义名称和类型建立顶层或下级节点、调整顺序和上级组织、删除未被使用的叶节点；层级深度不限，也不预置数据。列表读取成功时始终返回数组，没有节点时返回 `[]`。页面区分加载失败和空数据，读取失败时提供重试，确认加载成功后才允许编辑。接口拒绝不存在的上级、循环引用，以及仍有下级或角色引用时删除节点。普通管理员可以读取组织树，只有内置超级管理员可以修改。

新建或配置角色时可以选择多个组织节点。所选编号保存在 `roles.permissions.organization_node_ids`，写入前核对节点是否存在。这项关联属于管理元数据，不改变现有用户鉴权、模型权限、企业账务组织或数据可见范围。用户的角色分配仍使用 `users.role`。

验证命令：`go test ./controller -run 'TestManagedRoleLifecycle|TestGovernmentOrganizationTreeAndRoleReferences' -count=1`，以及前端 `RolePermissions.test.js`。Go 测试使用独立 SQLite；设置 `DSH_SKILL_INSTALLATION_TEST_POSTGRES_DSN` 时使用临时 PostgreSQL 模式，测试禁止使用生产凭据。
