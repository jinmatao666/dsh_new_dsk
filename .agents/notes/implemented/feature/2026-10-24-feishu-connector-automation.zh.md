# Agent Note: 飞书连接器与自动化连接器选择

Status: implemented

[English](2026-10-24-feishu-connector-automation.md) | 中文

## 问题

连接器目录需要只展示飞书、钉钉和微信，自动化需要在任务执行时使用明确选择的连接器。

## 决策

桌面 runtime 随包固定版本的官方 `lark-cli`，构建时校验 SHA-256，运行时通过原生 argv 调用，不把密钥交给子进程环境。飞书授权、配置和退出登录由连接器页面管理；业务命令由 `feishu_cli` 工具执行。

自动化任务保存连接器 ID。执行前重新检查授权状态，只向任务会话开放已选择的连接器工具。任务不选择连接器时，连接器工具全部不可用。微信只提供向最近一次入站消息对应的已绑定本人会话发送文字的工具，不提供任意联系人或群聊发送。

## Alternatives considered

**保留演示目录。** 这会让用户误以为未实现的卡片可以执行真实操作，因此目录只保留三条真实入口。

**在自动化中复用聊天框选择。** 定时任务没有稳定的聊天框状态，任务持久化自己的选择并在执行前重新校验。

**开放微信任意收件人发送。** 当前微信通道只保存绑定用户的最近回复上下文，开放任意收件人会扩大授权范围，因此暂不提供。

## Consequences

固定版本 CLI 可能先保存用户身份并输出带缺失权限的 `authorization_complete` 事件，再以 3 退出。授权的两条输出流分别解析，登录身份和权限分别校验。经过校验的缺失权限名称可进入连接器状态；原始输出和设备码仍保留在 Host。CLI 刻意从推荐批量授权中排除 `im:message.send_as_user`，因此连接器提供明确的发送消息授权入口，并在业务缺权限后支持补充授权。缺权限时停止重试，直到 `auth check` 确认所需权限。创建应用和用户授权分别展示二维码阶段提示。

点击连接时将 CLI 未配置视为前置步骤：先初始化应用，再启动用户授权；已有配置则跳过初始化。同一个后台操作拥有两个阶段并阻止重复启动。完整授权链接作为不透明字符串原样保留；失败时展示经过校验的类别和子类型，不转发原始认证输出。

构建时导出固定 CLI 内嵌的官方 Skill 正文与参考文档，保留技能之间的相对链接，运行时无需下载。授权状态探测成功后，将文件安装到产品自己的技能目录，在 YAML 元信息之后补充桌面工具执行说明。每个目录的归属标记防止覆盖或移除其他技能。业务工具和自动化引导模型先读取共享与对应业务技能；授权仍由连接器页面管理。机器资源和脚本不在内嵌导出范围内。

飞书在互联网环境中可通过官方 CLI 覆盖消息、文档、日历和待办等业务域；首次使用需要配置应用并完成用户授权。CLI 二进制和授权状态探测不依赖 WebView 内的 shell。

飞书双向任务使用同一个自建应用的机器人身份，通过长连接订阅 `im.message.receive_v1`。Host 会用已授权用户校验每条事件，只接收该用户的个人私聊文本，复用或创建桌面 Session，再通过机器人回传结果。应用必须开启机器人、事件订阅以及机器人收发消息权限；停用或解绑会关闭通道，不会转发任意群聊或其他用户的消息。

自动化任务可能因连接器未授权、服务不可达或用户确认缺失而进入失败或等待状态。连接器选择只开放工具能力，不会在任务完成时自动推送结果。

## Verification

连接器与自动化 Host/Client TypeScript 项目通过定向 `tsc -b`；连接器 UI、DingTalk、WeChat 和自动化测试覆盖既有路径，飞书状态解析有单元测试。官方 CLI 运行时输出 `not_configured`，证明未配置时不会误报已授权。
