# Agent Note：按渠道选择和批量登记模型

Status: implemented

[English](2026-10-21-channel-model-configuration.md) | 中文

## 问题

模型页汇总所有渠道候选，使用浏览器控制的 datalist，且每次只能创建一个定义。只筛选表格而不筛选连通性请求，仍会调用无关来源。重复部分完成的登记可能造成重复定义或覆盖已有模型元数据。

## 决策

以已保存的渠道配置提供候选，通过不分页且不含密钥的目录读取。单个添加先选渠道，再使用等宽可搜索菜单，服务端校验归属。渠道筛选同步控制模型行、来源展示和连通性测试范围。批量弹窗要求主动勾选、逐模型确认，再逐项提交事务登记。

每项登记检查渠道当前模型清单；新模型的禁用定义、倍率与绑定原子创建，已有定义则只补缺失的默认分组绑定。重复提交不修改配置。失败明确展示，重试排除已完成项。界面沿用现有后台配色及间距，登记成功不表示上游已授权或支持图片。

## 备选方案

自动勾选获取的模型会混淆目录可见性和授权。为每个渠道生成别名会提前决定暂缓的调度及角色隔离设计。复用独立的定义、来源和系统选项写入会留下半完成的新模型。整个批次共用一个事务，则一个无效模型会让其他成功项一起回滚。

## 影响

模型在配置清单中不保证实际推理成功。批量新增后需主动启用。默认分组绑定沿用既有分组策略，不覆盖已有定义和其他绑定。既有单模型保存时的能力检测及通用来源编辑 API 保持不变。批量登记在进程内串行并锁定选项行；既有选项编辑器的读取替换语义、多副本内存缓存收敛不在本次范围内。

## 测试

实际页面 React 测试覆盖筛选、先选渠道、清除旧 ID、主动批量勾选、失败重试及搜索不等于选中。真实 Gin 请求和临时 PostgreSQL 模式覆盖登记、重复提交、渠道归属、保留配置、倍率失败回滚及不含密钥的目录。本地假上游验证筛选测试不调用其他渠道。无头浏览器检查实际后台、菜单宽度、批量勾选与确认，并检查批量登记不触发上游获取或能力检测。
