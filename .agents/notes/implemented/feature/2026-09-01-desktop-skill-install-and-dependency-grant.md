# Agent Note: Desktop skill installation and dependency grant

Status: implemented

English | [中文](2026-09-01-desktop-skill-install-and-dependency-grant.zh.md)

## Problem

Desktop users need an install action in the skill marketplace that creates a skill the local runtime can discover. Workspace Write sessions also need an explicit first confirmation before downloading a missing dependency without repeatedly interrupting one task after that consent.

## Decision

The OneAPI server owns published Skill packages and their immutable version history. The authenticated desktop host downloads a published package from the server; the renderer relays the package file set and SHA-256 digest to a native Tauri command, which validates the digest and manifest in a same-volume `.dsh/.dsh-skill-staging/` directory outside the watched skill root and then atomically publishes it to the current user's `.dsh/skills/<slug>/` directory. The management browser decodes the persisted package for its file tree, preview, and ZIP download instead of using a lightweight list record and synthesizing a single `SKILL.md`. The filesystem skill provider watches only that user root, and the native command notifies the live renderer to clear its slash-menu catalog cache after every installation, update, or removal. The next `/` query in the existing conversation therefore discovers the changed catalog without a browser refresh. Installation state comes from the filesystem rather than browser storage. Updates and removal accept only a matching marketplace manifest or a recognized legacy marketplace `SKILL.md`; unrelated same-name user directories remain untouched. [Dynamic skill release management](../architecture/2026-09-07-dynamic-skill-release-management.md) owns package publication and server storage.

Startup migration is idempotent for legacy published skills. It reconnects a legacy skill to an existing published release before creating a release, and leaves a colliding unpublished draft unchanged rather than aborting service startup or overwriting an administrator's work.

Skill category management owns the selectable marketplace category list. The desktop reads the ordered list and each published skill's `skill_package` relations from the server, so category creation, renaming, sorting, removal, and skill reassignment update both marketplace navigation and membership without a desktop rebuild. Marketplace navigation and personal-skill import never reconstruct missing categories from bundled or locally installed skills; an unavailable or empty server list leaves no selectable category. The legacy `skills.category` field is only a fallback for a published record whose relations have not been migrated. Administrators maintain a category name and optional description; category identifiers and package-type compatibility data remain server-managed. Import, metadata editing, and publication reject a missing or disabled category. Administrator ZIP import accepts an optional manifest, one wrapping directory, case-insensitive root `SKILL.md` and `manifest.json` names, and ordinary operating-system metadata files. It derives a stable technical slug when the supplied names are not kebab-case and replaces unsupported or oversized manifest icons with the system icon instead of rejecting the package. Path traversal, symbolic links, duplicate paths, decompression size, file count, file size, and directory depth remain validated before persistence. An imported skill records the authenticated uploader, falling back to `root` only when no account name is available.

Administrator prompt auditing stores only end-user text questions. Runtime-context snapshots, system instructions, Skill injections beginning with `<skill_content>`, `<skill_resources>`, or `<skill_instructions>`, tool framing, and empty text are rejected before persistence; the audit list also hides matching legacy records.

Users may add a complete custom skill directory through the marketplace. The browser supplies only files selected by the user; the native command validates every relative path, a UTF-8 root `SKILL.md`, its kebab-case name, file count, and total size in that same staging directory before atomically creating or replacing a marked directory under `.dsh/skills`. Scripts, templates, references, and other ordinary files retain their relative paths. The authenticated host uploads the validated file set as either an owner-only private skill or a public review submission. A private skill needs no review and never enters the public marketplace. A first public submission enters the administrator's “Skill Review” queue; approval creates a public immutable release. Editing an approved public skill creates an update review while the current public release remains installable, and only approval replaces it. Rejection keeps the submitted personal copy and records an explanation for another submission. Public display names may collide because marketplace identity uses a generated `community-<personal-skill-id>` slug; source badges, uploader identity, and icons distinguish official and personal entries. Private, pending, and rejected local skills appear only under “My installed”; ordinary marketplace browsing renders only server-published records. The administrator skill library presents official, approved personal-public, and private records as explicit filters. Private records never enter publication or review actions, but administrators can inspect and download their stored package as disclosed during upload. Only marked custom directories are removable from the desktop UI. Search and “My installed” use the actual filesystem state for official and custom skills.

The marketplace keeps each skill's kebab-case slug as its technical identifier while presenting the corresponding Chinese display name and concise Chinese function summary. “My installed” is a dedicated local list rather than a market filter: it omits featured and category navigation, exposes uninstall on every installed entry, and removes an entry after native deletion succeeds. Installation feedback is transient. The public server persists an official skill's install count only after the desktop has installed its downloaded package; personal imports never affect that count.

The marketplace ships three independent GIS_Service bundles—geological conditions, land-use planning review, and third-survey land-use analysis. Each bundle owns its `SKILL.md`, manifest, PowerShell invocation script, and API reference. The UTF-8-BOM scripts accept GeoJSON, a Polygon Shape file, a directory containing one complete Shape dataset, or a safe Shape ZIP. They validate the required `.shp`, `.shx`, and `.dbf` files, read polygon geometry and optional `.prj` coordinate-reference metadata, call the documented service endpoint through Windows PowerShell, and save timestamped raw JSON, Markdown, an analysis-view JSON, Excel, and Word artifacts in the workspace. The workbook contains a conclusion sheet and actual-response detail sheet, and the Word report carries the detailed professional analysis. The script asks the operating system to open the workbook after generation. They use the deployed GIS_Service URL by default and accept an explicit or environment-provided override. Each API reference defines the confirmed result fields the model may explain; the skills preserve unlisted fields without inferring planning or geological conclusions. Installed skill directories are read-only program resources during analysis; a failed invocation reports its error instead of rewriting the installed scripts.

The marketplace also ships ten independent office bundles for Word-to-PDF conversion, PDF organization, PDF page imaging, image-to-PDF composition, Excel cleanup, document comparison, document summarization, safe batch renaming, image optimization, and meeting minutes. Each package is installable and runnable by itself. Local scripts perform file conversion and extraction, never overwrite an input, emit machine-readable result markers, and accompany primary artifacts with concise Chinese reports. Their instructions install declared missing Python packages through the desktop dependency approval path and then retry the original operation. Document comparison separates paired replacements from excess inserted or deleted lines. Summaries require numeric and factual consistency checks. Image reports distinguish reduction from growth and identify individual files that became larger. Meeting minutes preserve relative dates and times unless the source states an exact value. Batch renaming always produces a preview before the model may request confirmation and apply the same mapping. Meeting minutes normalize supported audio to 16 kHz mono PCM WAV, divide long recordings into configurable 30–180 second segments, transcribe the segments sequentially through a configured OpenAI-compatible `/v1/audio/transcriptions` endpoint, join the text in source order, and use `qwen3.8-27b-fp8` at `/v1/chat/completions` for structured minutes; service URLs, model names, and credentials remain deployment configuration. One generator owns the package metadata and copies the reviewed runtime into each standalone bundle; a packaging command produces ten folders, ten ZIP archives, and SHA-256 checksums.

`ApprovalService` optionally remembers an allowed package-manager escalation for one live session. It recognizes only `pip`, `npm`, `pnpm`, and `yarn` install commands recorded on `bash` or `pwsh` tool calls. The first matching escalation reaches the normal human approval channel; later matching escalations receive an in-memory one-shot result without another prompt. Desktop enables this option through `DSH_DEPENDENCY_INSTALL_APPROVALS=session-once`; `pip --user` installs into the desktop-owned shared Python user base rather than an individual workspace or skill directory.

The deliverable row excludes helper source extensions and uses successful mutation locations or terminal artifact facts as its evidence. Office runtimes publish every created file in the `artifacts` array of one `WANWEI_RESULT` JSON line, including formats such as CSV, WebP, and HTML that are not part of the prose-oriented path fallback. Other terminal generators can still use an explicit generated, saved, written, output, or deliverable line. A GIS analysis-view JSON is rendered as a tabbed table card and hidden from ordinary file chips; matching Excel and Word files open from the card and remain listed as deliverables. It does not infer artifacts from assistant prose.

Every desktop release stages its Node runtime beneath a versioned resource directory derived from the release version. The native shell uses that same directory when it starts Node and the document helper. An upgrade therefore adds a new runtime rather than overwriting an earlier Sharp DLL which Windows may keep loaded. The NSIS hooks still terminate the visible current and legacy desktop executable trees before replacement, but do not probe or overwrite the previous runtime directory. This keeps normal upgrades independent of orphaned Node processes and security-software DLL handles.

The desktop release matrix builds Linux x64 on Ubuntu 22.04 alongside the existing native Windows and macOS targets. It installs the Tauri WebKitGTK and packaging prerequisites, stages the same desktop runtime, and publishes both `.AppImage` and `.deb` artifacts with the corresponding release upload.

## Alternatives considered

**Keep marketplace installation in browser storage** — rejected. A browser-only installed marker cannot place a skill in the host catalog or make it callable by a new conversation.

**Trust arbitrary renderer-provided source as an official package** — rejected. The renderer may relay an authenticated server response, but the native command validates every file path and the manifest before replacing a marketplace directory. Browser-selected source remains the separate custom-skill flow.

**Install every bundled skill on application startup** — rejected. Preinstalling the bundles makes them model-visible without a user choice and prevents the Marketplace from representing actual local state.

**Grant all later sandbox escalations after one dependency approval** — rejected. A package installation grant must not authorize unrelated commands or filesystem actions.

**Remember dependency grants across sessions** — rejected. A new task needs a fresh user decision and session persistence would introduce revocation and auditing requirements.

## Consequences

Installed marketplace skills are local to the desktop user and become available through the next slash-menu catalog fetch in the current conversation. The skill list contains published server entries and skills discovered on the local computer. The Marketplace UI can still render in a non-desktop browser, but only published server entries expose an enabled install action. A server version newer than the locally installed manifest appears as an update action; one click downloads and atomically replaces the package, then reports that the update succeeded.

The administrator's skill list is backed by server `skills` and `skill_releases` records rather than browser mock data; import, validation, publish, unpublish, and rollback update that source. Custom icon selection accepts PNG, JPEG, WebP, and GIF files up to 2 MB. The desktop marketplace reads the public server list after authentication, so server-side publish state takes effect when the marketplace refreshes. The server must enable its `remote_skills` capability for these routes.

The desktop sidebar exposes Automations, Connectors, Expert Teams, and the Marketplace as separate actions stacked above Settings. Each action owns its own overlay and navigation state; the Marketplace no longer uses top-level product tabs to switch among those surfaces.

The Automations overlay is a local presentation prototype: configured tasks, templates, execution history, and creation forms are kept only in component state. The interface explains that it does not schedule jobs, create a conversation, or access a connector until those services are deliberately introduced.

The Connectors overlay is also a local presentation directory. It uses bundled brand-styled SVG marks, compact cards, and per-connector details to show the intended authorization scope without collecting credentials or contacting third-party services. Custom entries remain in component state and are explicitly marked as demonstrations until a managed connector service exists.

The Expert Library separates individual specialist roles from specialist teams. The individual entries describe one future agent profile, while team entries describe future multi-role workflows and their skills. Both surfaces stay in local component state and must not imply that an agent or team is already provisioned or executing.

Marketplace installation uses the public Tauri bridge when available and falls back to the persistent Tauri internals bridge for external-sidecar pages. Installation and failure feedback appears briefly from both the skill list and a skill detail page.

Office bundles use the existing official-package publication and installation path, so their manifests appear in both the administrator projection and desktop marketplace catalog. Python dependencies are declared per bundle and loaded only by the operation that needs them. Word-to-PDF tries Microsoft Word, WPS, and LibreOffice for each input, continuing to the next converter after either startup or export failure. Document summarization and meeting minutes separate deterministic source extraction from model-authored synthesis, then render the reviewed Markdown result to a styled Word document. Meeting audio preprocessing uses FFmpeg only when the input is not already a standard WAV; temporary normalized and segmented files are deleted after serial transcription. The meeting service URL, model identifiers, segment duration, and FFmpeg location have deployment overrides, while the published defaults target the verified local deployment. This keeps unsupported OCR, semantic comparison, failed audio transcription, or failed synthesis from being reported as completed work.

The GIS_Service skills require polygon geometry with a coordinate reference compatible with the service. A Shape ZIP is extracted only to a temporary directory and removed after the request. Each invocation leaves timestamped raw JSON, Chinese Markdown, analysis-view JSON, Excel, and Word artifacts. The workbook is opened through the system file association and remains available through the produced-files row. The desktop reads only bounded timestamped analysis-view files and presents their conclusion and response-detail tables in the conversation. The report records the inspected input, coordinate reference metadata, confirmed response fields, record counts, and applicable area or zone results. The chat summary uses Chinese except for endpoint names, filenames, and field codes; it treats each response dataset as an independent statistical denominator and does not invent meanings for unlisted fields. Before packaging a workbook, each worksheet removes XML 1.0-invalid control code points while preserving valid tabs, line breaks, carriage returns, and surrogate pairs, then parses the generated worksheet XML. This prevents API or user data from producing a workbook Excel must repair.

The dependency convenience applies only after an existing escalation path and does not change Full Access behavior. It reduces repeated prompts without widening the session's general sandbox policy.

Workspace Write treats a pre-existing output filename as a user-owned choice. The agent asks whether to create a versioned file, read then overwrite the existing file, or cancel. Full Access lets the agent choose a versioned file or replacement without asking, but replacement still requires reading the existing file first.

## Verification

Focused approval and deliverable tests cover the session grant, source-file exclusion, and analysis-view rendering. GIS invocation checks cover GeoJSON, Shape ZIP, Shape directory, and direct Shape-file inputs, including timestamped JSON, Markdown, analysis-view, Excel, and Word artifacts. Office runtime smoke tests create real PDF, image, Excel, Word, text, and meeting fixtures and exercise every local operation; a separate Microsoft Word smoke test covers actual PDF export, and package validation covers all ten standalone manifests and archives. Server import tests cover manifest icon fallback, case-insensitive root files, operating-system metadata removal, slug normalization, path containment, and complete package persistence. Native tests cover complete-directory installation, authenticated-server package installation, updates, legacy migration, custom-directory validation, ownership refusal, removal, and restricted analysis-view reads. Type checking covers the marketplace, approval, and deliverables packages; Rust checks cover the desktop native commands.
