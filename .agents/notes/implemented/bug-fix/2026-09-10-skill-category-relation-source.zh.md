# Agent Note: 技能分类关系的数据来源

Status: implemented

[English](2026-09-10-skill-category-relation-source.md) | 中文

## Problem

分类管理列表此前通过旧的 `skills.category` 展示字符串统计和展开技能，而技能分配使用分类关系 ID。展示字段过期时，同一技能可能同时显示在“通用类”和“空间制图”下。分类改名后，名称与稳定编码也可能不一致；如果把历史编码“通用类”视为默认分类身份，就会错误拒绝其他名称分类上的操作。

## Decision

分类管理的数量统计、展开列表和删除校验均以 `skill_category_relations.category_id` 作为技能包分类的权威来源。旧的 `skills.category` 字段继续作为展示和兼容字段，并在技能包分配路径中同步，但不再用于推断后台绑定关系。主分类操作严格按展示名称解析；只有名称为“通用类”的技能包分类受到默认分类保护，且该名称不可修改。API 通过 `is_default` 返回这一身份，分类编辑器不再根据编码或本地标签推断。除此之外，分类编辑器只保存可编辑的名称和描述，稳定的分类编码和类型保持不变。

分类读取按技能和分类 ID 去重。批量分类查询还会选出全部排序表达式，以满足 PostgreSQL 对 `SELECT DISTINCT` 的要求。启动迁移清理重复关系行，以及合并重复分类后遗留的关系。移出请求同时携带分类 ID 和展示名称；如果历史响应把名称与错误 ID 配对，服务端会从该技能的实际关系中重新解析同名分类，再把该技能的主分类关系替换为默认分类。

分类表格使用类型、稳定编码和数据库 ID 组成的复合键区分可展开行。请求序号阻止先发但较慢的响应覆盖当前展开行。技能库页面分别加载技能与分类元数据，因此一个接口失败不会丢弃另一个接口已成功返回的数据。

## Alternatives considered

**只修复旧展示字段。** 现存数据在迁移完成前可能保留旧值，后续写入也可能再次造成不一致。后台读取必须使用已规范化的关系 ID。

**立即移除旧字段。** 现有技能市场接口和技能包元数据仍公开该字段；移除它会把本次缺陷修复扩大为不兼容的接口变更。

**编辑时写回所有分类列。** 编辑器没有分类编码或类型的输入项。写回这些字段可能触发历史数据库索引冲突，且不会改变管理员实际选择的内容。

**用分类编码标识默认分类。** 编码在改名后保持不变，可能在分类已有其他可见含义时仍保留“通用类”。默认保护改为跟随准确的可见默认名称。

## Consequences

每一行分类都反映技能市场筛选和下载实际使用的关系。旧展示值、响应 ID 错配和重复关系行不会产生重复展开技能、让技能出现在错误分类中，也不会使非默认分类继承默认分类限制。PostgreSQL 可以执行去重批量查询，分类元数据接口失败也不会清空技能列表。快速切换分类时只保留最后一次展开请求的响应。
