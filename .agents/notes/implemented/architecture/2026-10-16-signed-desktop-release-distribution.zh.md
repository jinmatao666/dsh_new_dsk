# Agent Note: 桌面版本签名分发

Status: implemented

[English](2026-10-16-signed-desktop-release-distribution.md) | 中文

## 问题

手动分发安装包缺少“已上传候选包”和“管理员批准发布”之间的持久区分。仅对文件签名不能绑定上传时声明的版本和平台。

## 决策

OneAPI 持有不可变的平台／版本上传记录，以及事务更新的各平台发布指针。Runner 生成的 ZIP 同时携带签名清单和签名文件。服务在接受草稿前验证两者，发布前再次验证。只有超级管理员可变更版本，复用既有鉴权和操作审计。服务器与上传界面都不保存签名私钥。

清单绑定产品标识、正式版本、平台、文件名、字节数、SHA-256 和文件签名。导出器使用真实 Tauri 签名工具，不引入另一种签名格式。公开接口只返回严格高于客户端版本且系统／架构完全匹配的版本。撤下保留历史最高版本并关闭可用性，不回退。平台／版本唯一记录阻止替换先前上传内容。

原生壳使用嵌入的公钥验证两份签名，使 HTTP 传输后仍能验证清单绑定关系。检查自动进行，下载和安装则分别由用户决定。父子进程私有 stdin 交互在一个同步准入区间内完成最后的忙碌拒绝及冻结新工作。Host 等待整个插件树清理完成后才确认正常退出，原生父进程还会等待进程成功退出，再调用维护中的 Tauri 安装器。超时不能授权安装。

## 考虑过的替代方案

**直接从 GitHub 发布。** 操作者需要在现有自建后台可视化批准发布，并与仓库迁移解耦。因此 Runner 输出是待上传产物，不直接发布。

**只验证安装包签名。** 合法旧包可以在未签名清单中被标为高版本。第二份签名绑定发布元信息，无需服务器持有私钥。

## 影响

服务需要配置公钥、共享的持久文件存储和新增数据库表。HTTP 可用，但不能保护更新可用性或未签名的更新说明免受网络篡改。完整包上传要求相应代理限制。服务保留历史数据；突然终止可能留下未引用的暂存目录。发布失败不改变先前指针。

使用一次性密钥和隔离 SQLite 数据库，联合验证真实 Tauri CLI 签名及真实 Gin／超级管理员鉴权的上传、发布处理器。同一发布 ZIP 验证原生清单与文件验签。界面测试覆盖管理员发布和原生检查控件。Loader 组合的真实 Agent 验证运行、维护拒绝和清理顺序，隔离产品后台验证清理确认及随后退出。真实 Windows／macOS／Linux 安装器升级仍为人工发布验收要求。原生内存下载最多占用 2 GiB，不持久保存。清理失败可能使当前运行时不可用；更新器拒绝安装并要求人工重启，不强制继续。没有取代已有决策，产品叠加层归属保持不变。
