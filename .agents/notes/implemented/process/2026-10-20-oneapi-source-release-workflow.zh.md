# Agent Note: 已提交 OneAPI 源码的发布流程

Status: implemented

[English](2026-10-20-oneapi-source-release-workflow.md) | 中文

## 问题

为每个版本分别维护打包和部署脚本需要人工修改，也可能悄然收集共享工作区中的无关改动。发布需要可识别的源码提交和可重复执行的操作命令，不能自动发布尚未完成的后台修改。

## 决策

[发布命令](../../../../scripts/oneapi-release/release.mjs) 从明确的 Git 引用打包已提交的 OneAPI 文件，并拒绝未提交的后台改动。归档过滤使用私有临时 Git 索引，不改动用户暂存区。所选提交同时维护两个 npm 锁文件、部署脚本和构建检查；锁文件缺失或不匹配时预检失败，而不是在打包时生成浮动依赖。

每个版本拥有独占的输出目录、源码 tar、提交信息、校验值和自动生成的服务器命令。[固定部署脚本](../../../../scripts/oneapi-release/deploy-oneapi.sh) 不经 shell 求值解析元数据，校验归档内容和镜像来源，保留既定容器配置，并仅在状态接口报告目标版本时接受启动成功。前后端回归检查放在已提交的 Dockerfile 中，不在发布时进行文本替换。

统一仓库同时维护离线资源后台和签名桌面更新发布功能。资源处理器、部署配置校验、接口和管理端资源面板与更新包接口、审计动作同时保留。从独立工作副本迁入时只补充缺失的资源功能，不替换更新发布实现、依赖版本或同事的远端提交。历史交付归档保持不变。

桌面更新公钥由部署脚本维护，因为仅替换镜像会继承旧容器缺失公钥的状态。纳入校验的脚本携带公钥、补齐缺失设置，并拒绝隐式密钥轮换。只有没有现有挂载覆盖且容器目标路径不存在时，默认更新存储才补充专用持久化挂载。已有未挂载数据要求明确迁移，不能用挂载隐藏。服务器不接收签名私钥或密码。启动后的检查核对已应用的公钥和可写持久化挂载，全部通过才接受部署。下载路由由[复用当前后台的更新器](../architecture/2026-10-16-signed-desktop-release-distribution.zh.md)维护，不依赖特定部署的公网地址。

## 考虑过的替代方案

**打包当前工作目录。** 这会混入未完成的协作改动，使部署源码难以复现，因此命令要求后台文件先提交。

**每个版本生成不同的部署脚本。** 这会重复维护安全修复和人工替换。元数据驱动的脚本只维护一份实现，并在各发布包中记录其确切字节内容。

**立即依赖 CI 和镜像仓库。** 这会增加基础设施和服务器连通性要求。源码包保留现有服务器侧 Docker 构建方式，后续 CI 可以调用同一个打包入口。

## 影响

操作员仍需上传版本目录、选择数据库备份策略并验收部署后的应用。容器恢复不能撤销数据库迁移。离线测试覆盖 Git 打包、归档拒绝、挂载保留和 Docker 创建参数复制；真实 Linux 镜像构建与回滚需在服务器侧验证。打包不会合并远端改动、提交其他开发者文件或更新生产环境。
